# KanQ 性能笔记

单张 RTX 4090（sm_89，CUDA 12.8）上的实测与归因。数字全部来自 `kanq-test bench` 与矿池实跑，
没有推算值。改内核前先读 §3「不要再试的」。

## 0. 现状

| 实现 | 4090 速率 | 备注 |
|---|---|---|
| **KanQ 1.2** | **~920 MH/s** | `bench 8` 923.6；矿池实跑 916–922，share 被接受 |
| KanQ 1.1 | ~900 MH/s | prestate + 惰性归约 |
| KanQ 1.0 | 75–100 MH/s | 协议正确，内核朴素 |
| 官方 quantus-miner CUDA v4.2.0 | 862–886 MH/s | 官方 `docs/vast-gpu-benches.md` |
| fl4shminer 1.4.3（闭源） | 1.22 GH/s | 同卡实测；内核不可见 |

share 难度 18,253,611,008 时 920 MH/s 约 20 秒一个 share。同一张卡不要跑两个矿工实例：速率腰斩、功耗从 255 W 掉到 119 W。

## 1. 1.0 → 1.1：9× 的量化归因

差距 = **单次 permute 慢 6× × permute 次数多 2×**。

| 错误做法 | 后果 | 正确做法 |
|---|---|---|
| 索引放在 nonce[4:12]（高 32 字节） | midstate 用不上，每 nonce 4 次 permute | 索引放 nonce[56:64]，主机算 prestate，GPU 每 nonce 2 次 permute |
| 每次 `gf_add` 完整归约 + 规范化（≈10 指令），一次 permute 上千次 | 加法开销 3× | 惰性：值在 [0,2^64)，加法一次折叠（5 指令）；线性层 96 位累加只归约一次 |
| `reduce128` 用两次 64×64 乘 EPS 再逐个修进位（≈15 指令） | 乘法归约 2.5× | 6 指令 `mad` 折叠（2^64≡EPS，2^96≡−1），两处 2^-33 回绕不修，主机复核 |
| 30 轮 `#pragma unroll` 全展开 | 二进制 12.6 MB，编译 10–15 min，指令缓存击穿 | 轮循环不展开或小幅展开，轮常量走 `__constant__` |
| `unsigned __int128` 做域运算 | 6.9 MH/s | 纯 64 位 + `__umul64hi` / `mad.wide` |
| `recv` 300 ms 超时阻塞 | 内核 20 ms/轮时 GPU 闲 90% | `MSG_DONTWAIT`，网络 I/O 与内核异步重叠 |

launch 参数（每线程 nonce 16/32/128 × 块数 4096/8192 × 驻留块 4/3/2）实测全部在 871–897 MH/s，不是杠杆。

## 2. 1.1 → 1.2：为什么停在 ~900，还差 fl4shminer 多少

### 2.1 工具限制

- 测试机是 LXC 容器，宿主驱动未放开 `RmProfilingAdminOnly` → `ncu` 报 `ERR_NVGPUCTRPERM`，拿不到硬件计数器。
- fl4shminer 是 64 MB Go 二进制，内核不在明文 fatbin 里（`cuobjdump` 找不到设备代码），且启动时检测分析工具直接退出。

所以只能：静态 SASS（`cuobjdump -sass`）+ 自建微基准（`clock64()` 计时的直线代码块）。

### 2.2 内核静态账本（每 permute 13,604 条 SASS）

| 部件 | 每 permute 指令 | 占比 |
|---|---|---|
| S-box x^7（118 次 × ~54） | ~6,400 | 47% |
| 部分轮 12 次对角乘 + 归约（22 × ~192） | ~4,200 | 31% |
| 外部线性层（8 × ~326） | ~2,600 | 19% |

真正的乘法只占 ~17%（IMAD.WIDE 168 + IMAD.HI 60 / 全轮 902），其余是加法、进位和搬运。

### 2.3 sm_89 整数管线实测（1024 条直线 SASS，8 warp/调度器）

| 指令 | IPC/调度器 | 说明 |
|---|---|---|
| IADD3 | 0.99 | ptxas 把一半转成 `IMAD.IADD` 走 FMA 管线才到 1.0 |
| IMAD / IMAD.WIDE / SHF / SEL | 0.50 | 单管线 16 lane，每 warp 2 周期 |
| **IMAD.HI.U32** | **0.25** | 四分之一速，占 FMA 管线 4 周期 |
| 3 IADD3 + 1 IMAD.HI | 0.60 | 两管线各占：ALU 6 + FMA 4 |
| 64×64→128 乘（3 IMAD.WIDE 累加 + 进位） | **0.41** | 模型预测 ~1.0，实际一半；64 位累加/进位序列有静态看不见的损耗 |
| 直线代码 ≤ 64 KB | 0.99 | 指令缓存不是瓶颈（热代码只有 34 KB）；96 KB 起下降，256 KB 剩 0.35 |

模型：每子分区 ALU、FMA 两条 16 lane 管线，任何整数指令占其一 2 周期（IMAD.HI 占 FMA 4 周期），下限 = max(ALU, FMA)。
代回内核：全轮 ALU 940 / FMA 934（已配平）→ 每 permute 下限 14,692 周期，实测 22,878，**达成率 64%**。

### 2.4 占用率扫描

| warp/SM | 1 | 4 | 8 | 16 | 48 |
|---|---|---|---|---|---|
| 1.1 内核 MH/s | 146 | 584（线性） | 763 | 818 | 892 |
| 1.2 内核 MH/s | 181 | 720（线性） | 911 | 943 | 930 |

每调度器 1 个 warp 完全线性，2 个就饱和，之后几乎不涨 → 不是延迟受限，是与占用率无关的吞吐上限。

### 2.6 直线展开（P1，2026-09-20，RTX 3090 sm_86 / CUDA 13.2）

PeakMiner 的内核是 17.7k 条零循环直线代码（283 KB）。把我们的轮循环全展开（编译开关 `QPOW_UNROLL`，
0 = 1.2 基线 / 1 = 单 permute 直线 / 2 = 整个 hash 直线），三档三道自检都 38/38，无溢出：

| 档 | mine_kernel SASS | 寄存器 | nvcc | npt=16 MH/s | npt=1 | npt=4 |
|---|---|---|---|---|---|---|
| 0 | 4,136 条 ≈ 64 KB，LDC 40 | 94 | 14 s | **400 / 397 / 394** | 399 / 392 | 399 / 394 |
| 1 | 12,744 条 ≈ 199 KB，LDC 1 | 94 | 26 s | 372 / 370 / 368（−7%） | 401 / 397 | 399 / 395 |
| 2 | 24,808 条 ≈ 387 KB，LDC 1 | 96 | 36 s | 353 / 349（−12%） | 401 / 395 | 399 / 396 |

（npt = 每线程 nonce 数，矿工默认 16；每格是交错跑的各轮，块数 4096。）

- 直线化确实少 9% 指令（24.8k 静态 vs 基线 27.2k 动态），轮常量也从 LDC 变成 `c[3][imm]` 操作数，
  但吞吐没涨反跌，且**跌幅随 npt 增长**（npt=64、1 块/SM 时 −24%）：warp 在 nonce 循环里逐渐漂移，
  387 KB 的直线代码超出指令缓存后每个 warp 各自取指。npt=1 就是 PeakMiner 的几何（每线程每 launch 一个 hash，
  所有 warp 天然同步），这时三档持平。
- `QPOW_LOCKSTEP`（每个 nonce 前 `__syncthreads()` 拉齐块内 warp）在 npt=16 下把 2 档拉回
  402 / 399 / 405 / 400 vs 基线 400 / 397 / 400 / 397：4 组配对全部略高，均值 **+0.7%**——省下的 9% 指令
  几乎全被取指延迟吃掉。1 块/SM（8 warp）时 lockstep 无效（302 vs 379）：8 个 warp 同步后**一起**撞同一个
  取指 miss，没有别的 warp 掩盖；要靠第二个驻留块错开。压寄存器到 80 换 3 块/SM 又溢出（76 B），2 档掉到 356。
- 结论：直线展开在 sm_86 上**最多持平**，不采用（默认 `QPOW_UNROLL=0`，开关保留）；sm_89 未测。
  它同时解释了 PeakMiner 的两个特征：H=1 固定几何是直线代码的**必需品**而非选择，REG 48 是为了多驻留 warp
  掩盖取指延迟，而他们 54% 的达成率（我们 64%）就是这笔取指税。**同口径下他们 17.7k 条 vs 我们 24.8k 条 = 1.40×，
  减去取指税正好是实测的 1.32×：差距 100% 是指令数**，唯一杠杆仍是 32-limb 乘法器（P0）。

## 3. 结论与不要再试的

1. 可控杠杆只有"减指令数"，而现有算法形态里 83% 的指令是加法/进位/搬运，已经很紧；所有变体的天花板是 ~910–925 MH/s。
2. 36% 的达成率缺口来自 64 位累加/进位序列的微架构损耗，CUDA C 层面不可控，占用率也救不了。
3. fl4shminer 的 1.22 GH/s（= 我们管线下限的 88%，或指令数少 25%+）只可能来自换算法形态：把部分算术挪到闲置的 16 条 FP32-only lane，或手写 SASS 级调度。两者都是以周计的工程。
4. **不要再试**：launch 参数、`QPOW_MIN_BLOCKS`、展开深度（含全直线，§2.6）、去 IMAD.HI、移位改加法、
   CUDA C 形态的 32-limb 乘法（i64 中间量让指令数 +47%）——都测过了，数据在上面。

## 4. 改内核的门槛

```
./build/kanq-test fieldtest                 # 域运算 + permute(0) 对参考值
./build/kanq-test selftest vectors.txt      # 主机精确 + GPU 惰性各 38/38
./build/kanq-test pstest   vectors.txt      # prestate 分解 + GPU 挖矿路径 38/38
./build/kanq-test bench 8                   # 之后才谈速率
./build/kanq --wallet <addr> --once         # 真实矿池拿到一个被接受的 share
```

GPU 惰性路径 38/38 必须全过：出现失败就是 bug 不是"误差"（惰性归约的预期误差率 ~3e-7/哈希，38 组里撞上的概率可忽略）。
